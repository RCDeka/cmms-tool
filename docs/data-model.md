# Data Model

Database: PostgreSQL 16, managed with Prisma migrations. All primary keys are UUID (`uuid`, generated by the database via `gen_random_uuid()`), except where noted. All timestamps are `timestamptz` in UTC.

## Entity Overview

```
User 1───* WorkOrder (assignee)
User 1───* WorkOrder (createdBy)
User 1───* WorkOrderStatusHistory (changedBy)
Location 1───* Location (parent/children)
Location 1───* Asset
AssetCategory 1───* Asset
Asset 1───* WorkOrder
WorkOrder 1───* WorkOrderStatusHistory
```

## Enums

### Role
| Value | Description |
|---|---|
| `ADMIN` | Full access, user management |
| `MANAGER` | Manages assets and work orders, sees dashboard |
| `TECHNICIAN` | Executes assigned work orders |

Roles are a Postgres enum on `User.role` (one role per user). A separate Role table is intentionally avoided for the MVP.

### AssetStatus
`ACTIVE`, `INACTIVE`, `UNDER_MAINTENANCE`, `RETIRED`

### WorkOrderStatus
`OPEN`, `IN_PROGRESS`, `ON_HOLD`, `COMPLETED`, `CANCELLED`

- Terminal statuses: `COMPLETED`, `CANCELLED`.
- "Open" in KPIs means non-terminal: `OPEN`, `IN_PROGRESS`, `ON_HOLD`.
- "Closed" means terminal.

### WorkOrderPriority
`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`

### WorkOrderType
`CORRECTIVE`, `PREVENTIVE`, `INSPECTION`

## Business Rules

### Users and roles
- BR-U1: Email is unique, case-insensitive (normalized to lowercase).
- BR-U2: Only `ADMIN` can create users, change roles, or deactivate users.
- BR-U3: Users are never hard-deleted; they are deactivated (`is_active=false`). A deactivated user cannot log in.
- BR-U4: The last active `ADMIN` cannot be deactivated or demoted.
- BR-U5: A user with open work orders can be deactivated only after those are reassigned (409 otherwise).

### Assets
- BR-A1: `code` is unique and immutable after creation.
- BR-A2: An asset requires a category and a location.
- BR-A3: Assets are soft-deleted (`deleted_at`). An asset with non-terminal work orders cannot be deleted (409).
- BR-A4: Work orders cannot be created on assets with status `RETIRED` or soft-deleted (422).
- BR-A5: Locations and categories referenced by assets cannot be deleted (409).

### Work orders
- BR-W1: A work order must reference an existing, non-retired asset and an active assignee at creation (both NOT NULL).
- BR-W2: The assignee must have role `TECHNICIAN` or `MANAGER` and be active.
- BR-W3: Initial status is always `OPEN`. A history row (`from_status=NULL`, `to_status=OPEN`) is created in the same transaction.
- BR-W4: Allowed status transitions (all others rejected with 409):

| From | To |
|---|---|
| OPEN | IN_PROGRESS, CANCELLED |
| IN_PROGRESS | ON_HOLD, COMPLETED, CANCELLED |
| ON_HOLD | IN_PROGRESS, CANCELLED |
| COMPLETED | (terminal) |
| CANCELLED | (terminal) |

- BR-W5: Every status change writes a `work_order_status_history` row in the same transaction.
- BR-W6: `started_at` is set the first time the order enters `IN_PROGRESS`. `completed_at` is set on `COMPLETED`.
- BR-W7: Moving to `COMPLETED` requires non-empty `resolution_notes`. Moving to `CANCELLED` or `ON_HOLD` requires a `comment`.
- BR-W8: Terminal work orders are read-only (no field edits, no reassignment).
- BR-W9: `asset_id` is immutable after creation. `assignee_id` can be changed by `MANAGER`/`ADMIN` on non-terminal orders.
- BR-W10: `TECHNICIAN` can see all work orders but can only change the status of orders assigned to them; cannot create, reassign, or edit fields other than `resolution_notes`.
- BR-W11: Optional side effect (keep simple): when an order enters `IN_PROGRESS` on a `CORRECTIVE` type, the asset is not automatically modified. Asset status is changed manually.
- BR-W12: `due_date`, if provided, must not be earlier than the creation date.

### KPI definitions
- Open work orders: count with status in (`OPEN`, `IN_PROGRESS`, `ON_HOLD`).
- Closed work orders (period): count with status `COMPLETED` and `completed_at` in the period. Cancelled orders are reported separately and excluded from MTTR.
- Overdue: non-terminal with `due_date < now()`.
- MTTR (hours): average of `completed_at - created_at` over `COMPLETED` orders of type `CORRECTIVE` with `completed_at` in the period. Returns `null` if none.
- Workload per technician: count of non-terminal orders by `assignee_id`, with a breakdown by status, plus completed count in the period.
