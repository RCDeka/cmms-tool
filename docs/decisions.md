# Decisions

This file records the answers to the open questions of the product brief (`docs/SPEC_MVP_CMMS.md`, section "Open points") and every place where the implementation docs deviate from or complete the brief. When a decision changes, update it here in the same commit.

## Reference hierarchy

1. `docs/SPEC_MVP_CMMS.md`: product brief. Source of truth for **intent and scope**. It is the English translation of the original French brief, which is kept in git history (commit `4f07659`, `docs/SPEC_MVP_GMAO.md`).
2. `docs/data-model.md`, `docs/api-design.md`, `docs/architecture.md`, `docs/ui-guidelines.md`: refined implementation contract. Source of truth for **how**. Where they differ from the brief, the difference is listed below.
3. `docs/roadmap-mvp.md`: order of work and acceptance criteria.
4. `docs/spec-preventive-maintenance.md`: specification of the preventive maintenance phases (D48). What a phase implements is described in the documents of level 2, which prevail; D49 lists where Phase 17 completes or departs from the specification.

## Answers to the brief's open questions

| # | Question | Decision | Rationale |
|---|---|---|---|
| Q1 | Backend: Flask or Express? | **Node.js 24 LTS + Express 5** | Same language as the frontend; `better-sqlite3` is fast, synchronous and simple. |
| Q2 | Authentication: home-made token or JWT library? | **JWT via `jsonwebtoken`**, passwords hashed with **argon2** | Standard, audited libraries; no home-made crypto. |

| Q6 | Application name | **"Tacto"**, defined in one place (`APP_NAME` in the frontend config) | Chosen by the product owner. First named "Fast-CMMS", renamed "Tacto" on 2026-10-09 (D58). |
| Q7 | Concurrent users | Target **up to ~50 concurrent users**; SQLite in WAL mode with `busy_timeout` | Ample for an internal MVP; one writer at a time is fine at this scale. |

## Deviations and additions to the brief

| ID | Topic | Decision |
|---|---|---|
| D1 | Passwords | `users.password_hash` added (the brief's table has no password column). |
| D2 | Versioning on assets | `version`, `has_conflict` and `updated_by` added to `assets` (the brief's `PUT /api/assets/:id` requires a version, but the table lacked it). `updated_by` also added to `work_orders`. |
| D3 | Conflict storage | New table `conflicts` stores the rejected client version and a snapshot of the server version. The entity row keeps the server version. |
| D4 | Record locked during a conflict | While a record has an open conflict, every `PUT` on it is rejected with `409` (`locked: true`) until a supervisor resolves it. Guarantees at most one open conflict per record. |
| D5 | People references on work orders | The brief's free-text assignee and supervisor become foreign keys `assignee_id` and `supervisor_id` → `users.id` (needed for "My work today" and permissions). The API also returns display names. `assets.responsible_technician` stays free text. |
| D6 | Integrity | `UNIQUE` on `assets.code` and `work_orders.number`; `CHECK` constraints on every enumerated column. |
| D7 | Detail loading | List endpoints return **complete records**, so the client stores each row as a detail record directly. This replaces the brief's one request per row (50 requests per page). `GET /:id` is used only on a cache miss or for revalidation. |
| D8 | Extra endpoints | `GET /api/health`, `GET /api/auth/me`, `GET /api/users`, `GET /api/reference-data`, `GET /api/conflicts`, `GET /api/conflicts/:id`, `GET /api/dashboard`. The brief needs them implicitly (supervisor console, dashboard tiles, dropdowns). |
| D9 | Offline reload | A small **service worker** caches the app shell (HTML, CSS, JS, vendor libraries), so the app also opens offline after a full page reload. API data is cached in IndexedDB only, never by the service worker. |
| D10 | Extra IndexedDB stores | `drafts` (standard-mode autosaves) and `sync_queue` (pending writes) added to the brief's five stores. Detail records are evicted together with their pages, except records that have a draft or a queued write. |
| D11 | Offline saves | The offline write queue applies to **both** save modes (the non-functional requirements say edits made offline are synced later). The modes differ only in what triggers a save. |
| D12 | HTML injection | The brief's `renderDetail` sample injects raw values into `innerHTML`. Every value must be escaped or set through `textContent`. |
| D13 | Dates | Datetimes are ISO 8601 UTC strings set by the application; dates are `YYYY-MM-DD`. "Today" and "this month" are computed in `APP_TIMEZONE` (default `Europe/Paris`). |
| D14 | Work order workflow | The brief defines statuses but no rules. Allowed transitions and required fields are defined in `docs/data-model.md` (BR-W4 to BR-W7). |
| D15 | Create / delete | The brief defines no `POST` or `DELETE`. **Creating work orders is in the MVP** (`POST /api/work-orders`, product owner decision), including offline. Creating assets and deleting any record were left out of the MVP, then added in Phase 8 (D34, D35); a work order is withdrawn by moving it to `CANCELLED`. |
| D16 | Language | Everything in English, enum values stored as codes. See Terminology above. |
| D17 | Third-party libraries | `idb` and `Chart.js` are vendored into `frontend/assets/vendor/` (no CDN, works offline). No bundler and no build step. |
| D18 | URLs | API and UI paths use plural kebab-case nouns (`/api/work-orders`, `/work-orders`). The brief mixed `bt` / `bons_travaux` / `bons-travaux`. A small entity config maps each entity to its IndexedDB prefix (`asset`, `wo`). |
| D19 | Runtime | Node.js 24 LTS (the brief doesn't specify a version). |
| D20 | Deployment | No Docker. Local development with npm, where Express also serves the frontend. Production: systemd service + Nginx reverse proxy + Let's Encrypt on the VPS. |
| D21 | Power-user mode | Determined by `users.power_user`; the seed sets it to `true` for supervisors and admins and `false` for technicians and staff. |
| D22 | Logout | Logout deletes the token and clears IndexedDB. If the sync queue is not empty, the user must confirm first. |
| D23 | Permissions | The brief defines roles but no permissions. The permission matrix is in `docs/api-design.md`. |
| D24 | Role name | The brief's "opérateur" means the person who carries out the work, so the role is `TECHNICIAN` ("operator" in English usually means a machine operator). |
| D25 | Work order author | `work_orders.created_by` → `users.id` added, so the creator of a work order is known. |
| D26 | Offline creation | The client generates a UUID `client_id` for each new work order. The server stores it (`UNIQUE`) and treats a second `POST` with the same `client_id` as a replay: it returns the existing record instead of creating a duplicate. This makes queued offline creations safe to retry. Until the server answers, the work order exists only locally, has no `number`, and is shown as "Pending creation". |
| D27 | Who creates work orders | All maintenance roles (staff members submit requests instead, D46). A technician can only assign a new work order to themselves; supervisors and admins can assign it to anyone or leave it unassigned (permission matrix in `docs/api-design.md`). |
| D28 | Service worker strategy | **Network first with a 4 s timeout, cache as fallback**, for the shell files and every navigation (served as `index.html`). Online users always get the current files, so there is no cache version to bump by hand and no "new version available" notice. Offline, or when the network hangs, the last copy seen is served. The shell is precached on install; `frontend/test/network-sw.test.js` fails if a file under `assets/` is missing from the precache list. |
| D29 | Draft frequency | Drafts are written to IndexedDB **1 s after the last edit**, in both save modes, instead of every 60 s (brief). A reload or a closed tab never loses more than the last second of typing. The modes still differ: standard users are asked before leaving and offered to restore a draft; power users' changes are queued automatically. |
| D30 | Phase split for conflicts | Conflict creation (BR-V3) and the lock (BR-V4) are implemented in Phase 4 with the `PUT` endpoints, because the 409 answer must carry a stored `conflict_id` from the start. Phase 5 keeps the conflict list, arbitration and the console. |
| D31 | Public files | Only the shell is served: `/index.html`, `/sw.js` and `/assets/*`, plus `index.html` for client routes. The rest of `frontend/` (`package.json`, tests, `node_modules`, tool configs) is never served, by Express (404) or Nginx (answers with the shell). Found during the Phase 7 security pass: Express used to serve the whole folder. |
| D32 | Production network and headers | The API listens on `127.0.0.1` by default (`HOST`), so only Nginx on the same host can reach it. Nginx serves the static shell itself, so it sets the same security headers as Express (`deploy/nginx/tacto-headers.conf`, CSP kept identical by a test). API answers carry `Cache-Control: no-store`; responses are gzip-compressed by Express and by Nginx. In production the JWT secret must be at least 32 characters. |
| D33 | Backups | `npm run db:backup` copies the live database with SQLite's online backup API (consistent while the app writes), checks the copy with `PRAGMA integrity_check`, stores it as one self-contained file (journal mode DELETE), and deletes copies older than `BACKUP_KEEP_DAYS` (14). A systemd timer runs it nightly. |
| D34 | Asset creation | Supervisors and admins create assets (`POST /api/assets`, `/assets/new`). The code is optional (automatic `AST-0501`, …) or typed (capitals, unique). Creation needs a connection: assets are office data entry, and offline creation would need temporary ids for little benefit; the form keeps a draft meanwhile. On assets, `site` is free text with the known sites as suggestions, so a new building can be added; work orders keep the list of existing sites. |
| D35 | Deleting records | Only assets can be deleted, only without any work order (their history must be kept: set Out of service instead), at the version the user saw, by supervisors and admins, online. Work orders are never deleted: they are withdrawn with `CANCELLED` (a pending creation can still be discarded before it reaches the server). |
| D36 | Actions that need the server | Buttons that cannot work offline carry `.online-only` (like `.ai-only`): disabled while offline, with a tooltip saying why. |
| D37 | Audit log | One append-only `audit_log` table for all records, written in the same transaction as each change (BR-L1). It holds field-level changes (`from`/`to`), rejected conflicting edits (`CONFLICT`) and resolutions (`RESOLVE`); the work order status timeline is read from it rather than from a separate status-history table. Reading it needs a connection: the history is not cached in IndexedDB (it is loaded when the History section is opened). Every role sees the history of the records it can read; the global log is for supervisors and admins. |
| D38 | Search and filters | Full-text search uses SQLite **FTS5** (external-content indexes kept in sync by triggers, `unicode61 remove_diacritics 2`: accents and case ignored, word prefixes). User text is turned into quoted prefix terms, so no FTS syntax is ever interpreted. It replaces the Phase 1 `LIKE` search, removing its accent limitation. Filters live in the URL. Filtered lists are not cached offline: only the unfiltered pages are (D10), which keeps the cache small and predictable. |
| D39 | User administration | Administrators manage accounts at `/admin/users` (online only): create with a starting password, edit name, role, site, specialty and auto-save mode, deactivate or reactivate, reset a password. Accounts are **deactivated, never deleted**, so work orders and the audit log keep their authors; the username never changes. Deactivation and password changes end existing sessions at once: tokens stay stateless JWTs, but the authentication middleware reads the user on every request and refuses inactive accounts and tokens issued before `credentials_changed_at` (BR-U7, BR-U8). Every user changes their own password at `/account` and gets a new token for the current session. Account changes are logged in `audit_log` (`entity_type = users`, never any password data) and shown to administrators only. |
| D40 | Suggestions from any page | A **Suggest an improvement** button at the end of the top bar, on every page, opens a dialog over the current page (the user still sees what they describe). The idea is saved in a `feedback` table with the page path and query, the page title (and the record open in the side panel), the screen width, the author and their role at the time. Sending needs a connection; unsent text is kept until sent. Rate limit: 30 per hour per user. Administrators read and triage them at `/admin/feedback` (New, Planned, Done, Declined). `npm run feedback:export` prints the open ideas as Markdown, grouped by screen, to plan the next updates. |
| D41 | Brand colors and logo | Black, red and white after Société Générale (product owner request, 2026-10-04): black sidebar and black primary buttons, red accents, white surfaces, pure gray neutrals. Red is never used for actions, so it doesn't compete with error messages. New logo: a red gear and a white wrench on a black tile (our own drawing; the bank's logo is not reused). |
| D42 | Table sort and top pagination | Suggestions #4 and #6 (2026-10-04). Asset and work order tables sort from their column titles (click: ascending, again: descending); the work order API gains `title`, `site` and `assignee` sort keys, with unassigned and undated work orders last in both orders. The sort lives in the URL with the filters and survives opening a record and the back button. Only the default order is cached on the device (as with filters, D38): caching every order would multiply the page store for little offline value. Long tables repeat the pagination above the table. |
| D43 | Dashboard by role | Suggestions #1 and #5 (2026-10-04). Supervisors and admins get a second chart, a status pie of the work orders created in the last 30 days (`stats.by_status`, no new endpoint). Technicians get no chart: their dashboard is about their own work. "My work today" becomes "My work" with a Today / Next 7 days switch (Today by default). "Next 7 days" (today to today + 6, `my_work_week`) is used rather than the calendar week, so the list is useful on any day, including a Sunday. |
| D44 | Technicians' default work order list | Suggestion #3 (2026-10-04). A technician opening the work order list without filters gets the work orders assigned to them, with "Assigned to me" checked. Unchecking it writes `mine=false` in the URL (all work orders); "Clear filters" returns to their own work. Links that carry filters (dashboard tiles) are applied as they are, so the list matches the tile's count. For technicians, this list is the plain list cached on the device for offline use (their own work is what they need on site); cached pages record the query they were fetched with, so a page saved for another role is never shown. |
| D45 | Multiple selection in filters | Suggestion #2 (2026-10-04). Status, priority, type, category, criticality, site and assignee filters accept several values: the filter bar shows each as a dropdown of checkboxes. In the URL and the API the values are comma-separated (`status=OPEN,ON_HOLD`), except sites, joined by `\|` because free-text site names can contain commas (D34). Values of one filter are OR, filters stay AND. The separate "Not finished" option is gone: it is the same three statuses ticked, and the control still says "Not finished" for that choice (dashboard links keep working). Assignee in the URL is now text (`4,5`), not a number. |
| D46 | Staff requests | Product owner request (2026-10-08). A new role `STAFF` for bank employees who are not in the maintenance team: they submit **requests** (tickets) and follow them, nothing else. A request **is a work order** (`created_by` = the staff member), so the maintenance team triages and works on it with every existing tool (filters, history, conflicts, dashboard); there is no separate ticket table to keep in sync. Staff use their own API (`/api/requests`: only their own requests, in a reduced shape without hours, supervisor or versioning) and are refused every maintenance endpoint (403). The form asks what, where (site + free-text **location**, as there is no room list yet) and, optionally, the kind of problem (category) and the urgency (priority); both lists start with **"I don't know"**, which leaves the field out: no category ("Unspecified"), priority `NORMAL`. The type is not asked: requests are created `CORRECTIVE`, and the maintenance team corrects it when triaging. Requests are created unassigned. A **comment** thread on every work order (`work_order_comments`, append-only) lets the requester add information or ask for news and the maintenance team answer; comments do not change the work order's version, so they never cause conflicts. The staff home page lists their open requests with a plain-words status and **next step** (Received → Assigned → In progress / On hold → Done, or Cancelled); "All my requests" lists every request. Staff pages need a connection (no IndexedDB cache): requests are office use, and offline creation would need the temporary-record machinery for little benefit; unsent form and comment text is kept while the app is open. Adding the role required rebuilding `users` and `feedback` (SQLite cannot change a `CHECK`): the migration runner now turns foreign keys off while migrations run and checks them before each commit. No notification is sent yet: the maintenance team sees comments in the work order panel. |
| D47 | Review of staff requests | Product owner request (2026-10-08). Every staff request is **reviewed by a supervisor or an admin** before any work: new columns `review_status` (`PENDING` → `APPROVED` or `REJECTED`; NULL for work orders created by the maintenance team), `reviewed_by`, `reviewed_at`, `review_note`. One action, `PUT /api/work-orders/:id/review`, either **approves and allocates** the request in the same step (an assignee, technician or supervisor, is required; the reviewer becomes the supervisor unless another is chosen; type, priority, category and due date can be set at the same time) or **rejects** it with a reason the requester sees (the work order becomes `CANCELLED`). While a request waits, the regular edit refuses to assign it or change its status (422 `BR-R7`): only the review does; other fields (location, category, …) can be corrected. The review is checked against the version the reviewer saw (409 when it changed) and is not queued offline: it is a decision made online, like asset deletion (D36). Supervisors and admins get a dashboard tile **"Staff requests to review"** (`kpis.requests_to_review`, attention style when above zero) that opens the work order list with the new filter `to_review=true`. Staff see "Waiting for review", then "Approved" with the assigned person, or "Rejected" with the reason. Migration `007` marks requests sent before it: still open and unassigned → `PENDING`, cancelled → `REJECTED`, others → `APPROVED`. |
| D48 | Preventive maintenance (specified) | Product owner discussion (2026-10-08). Preventive maintenance moves from non-goal to **planned scope** (Phases 17–20), specified in `docs/spec-preventive-maintenance.md`. Two separate tools: a **year planner** (52 ISO weeks × maintenance plans, drag a plan to its starting week and the frequency repeats it, balanced per week against capacity by trade and site, with KPI tiles) and a **week scheduler** (days × technicians: a total of hours per technician per day, no clock times, 30-minute steps, 7 h capacity by default, blocks of at most 3 h 30, jobs split over days or technicians, travel/preparation/other time added by the supervisor, appointments lockable at a time by the supervisor or the technician, Monday–Friday with Saturday/Sunday opened per week). The year planner releases each week's work orders 4 weeks ahead into the scheduler's "to schedule" tray, next to corrective work and approved staff requests. Weekly capacity counts **technicians and supervisors** (by specialty), minus a **corrective reserve set by the administrators** (30 % by default). The brief kept preventive maintenance out of the MVP; this is a post-MVP extension. Phase 17 is implemented (D49). |
| D49 | Preventive maintenance, Phase 17 | Implementation choices of plans and the read-only year planner (`008_preventive_maintenance.sql`). **Occurrences** are stored from the current week to 104 weeks ahead, on the series of the anchor week (an anchor in the past is allowed: the series goes on from today on its own weeks); the daily release tops them up. The planner shows 52 (or 53) weeks starting between 104 weeks back and 52 weeks ahead. **Release** (BR-P6): daily job `npm run pm:release` (systemd timer at 04:00), `POST /api/planning/release`, and every `GET /api/planning/timeline`, which releases first so its chips are current (idempotent, so a read with this side effect is safe). There is no system user: automatic releases are written in the name of the plan's author, a release asked by someone in theirs. A released work order is `OPEN`, `NORMAL`, unassigned (the week scheduler assigns it in Phase 19), due on the Friday of its week, or today when the release is late. **Work order follow-up**: cancelling a released visit's work order skips the occurrence (BR-P7, which keeps its `work_order_id`: the `CHECK` is `RELEASED ⇒` a work order and `PLANNED ⇒` none, rather than the specification's equivalence); closing it in a `FLOATING` plan moves the plan's anchor to the closing week + the frequency (BR-P5, logged on the plan). **Capacity** (BR-Y2) is, until capacity overrides and open weekends arrive (Phase 19), 5 days × `daily_hours` per active technician and supervisor, minus the reserve. The site and trade filters narrow the capacity to the people of that site and specialty; building, type and search narrow the planned hours only (people have no building). A trade with visits but no specialist has no load ("No specialist" on the trade balance tile) rather than borrowing the general capacity. **Deferred**: allocations, capacity overrides and schedule weeks (Phase 19), blocked weeks and their warnings (Phase 18); `PUT /api/plans/:id/anchor`, occurrence moves and skips (Phase 18). `plan_id` and `planned_week` are read-only on work orders until the week scheduler. **Plans** are never deleted (`is_active = false` removes their planned visits and keeps the history), are edited at the version the user saw (409 when stale, no conflict console), and are searched with `LIKE` on code, title, site, building, location and supplier (a small table: no FTS index, so accents count). `end_week ≥ anchor_week` is checked by the API, not by a `CHECK`, because a floating plan's anchor moves. The planner needs a connection (P18) and is not cached on the device. |
| D50 | Asset picker | Product owner request (2026-10-08): nobody knows asset codes by heart. The asset field of the plan and work order forms keeps its code input (fast for those who know it, and still the only way offline, from the cached assets) and gains a **Browse assets…** dialog over `GET /api/assets`: full-text search, site, trade and status filters, the API's sortable columns, 20 rows per page, and the columns that tell assets apart (location, trade and subcategory, status, criticality). It needs a connection: large asset lists are searched on the server rather than cached whole on the device (D38). No new endpoint. |
| D51 | Year planner editing, Phase 18 | Implementation choices of the planner editing (`009_planner_editing.sql`). **Series moves** (`PUT /api/plans/:id/anchor`, or dragging the first planned visit of a row): the specification (BR-P2) keeps visits moved by hand and visits with a work order where they are, which left a quarter with two visits (the kept visit and the new series' one). So a series moved at the same frequency **shifts**: a visit moved by hand moves by the same number of weeks, keeping its own offset; a visit with a work order, or skipped, keeps its week but its due week follows the series while still to come, holding its slot (the unique `plan_id, due_week` then stops the daily top-up from planning a visit next to it). A frequency change rebuilds the series instead, dropping visits moved by hand that leave it; a floating restart (BR-P5) is a rebuild too, since the closed visit must not hold a slot. **Occurrences get a `version`** for moves, skips and restores (409 when stale). **Skipped visits can be restored** (`POST …/restore`), so a skip can be undone; a skip caused by a cancelled work order cannot. **Moves into the past** are refused for one visit; a series anchor may lie in the past (the series goes on from today). **Blocked weeks** are not in the audit log (planning hints, not records). **Live impact** is computed in the browser from copies of the rules (`planning-rules.js`, checked against the server's by a test), so dragging needs no request; only the drop is sent. **Undo / Redo** last while the planner is open; each step re-reads the record and refuses if it is no longer as the change left it. Moving a visit into the release horizon releases it at the next timeline load, after which it can no longer be moved or undone (BR-P4). |
| D52 | Week scheduler and My week, Phase 19 | Implementation choices of the week scheduler (`010_week_scheduler.sql`: `allocations`, `capacity_overrides`, `schedule_weeks`). **Hours left** (BR-S2) = the estimate rounded up to the half hour minus every `WORK` block of the work order, whatever its week; a carried-over work order is listed even when its blocks cover its estimate ("Fully scheduled"), so the supervisor can give it more time. **Planned week**: a work order without one takes the week of its first block (and, unassigned, the first person given a block as assignee, BR-S3); both are logged on the work order (`note: { schedule: true }`) and increase its version. `planned_week` was read-only in the work order form at first (editable since D55). **Tray** of a week: unfinished work orders not waiting for a review, planned that week, carried over from an earlier week (also when a later week is shown, as what would carry over), or without a week; opening the scheduler runs the release first (BR-P6), like the planner. **Longest block**: the planning setting `max_block_hours` (3.5 h by default, 422 above it); the column allows up to 8 h, the setting's maximum. **Appointments**: overlapping ones of a person → 409; a locked block cannot be moved, resized or removed (unlock first); the interface offers start times from 06:00 to 22:00, the API accepts 00:00 to 23:30 ending by midnight. Blocks of a finished work order are history: they no longer change (422 `BR-S4`). **Not logged**: the order of a day (`PUT /schedule/day-order`, which needs no version either, only the exact list of the day's blocks: 409 when it changed), capacity overrides and open weekends (planning details, like blocked weeks); blocks themselves are logged. | D53 | Balancing assistant, Phase 20 | Implementation choices of "Suggest a smoother plan" (`POST /api/planning/suggestions`, BR-B1 to BR-B4; no migration). **On the server**, a pure greedy rule (`rules/balancing.js`) over the timeline of the range and filters shown: it moves single planned visits only (no series move, no visit with a work order, no contractor visit), one at a time, choosing the move that lowers the most the sum of squared weekly loads plus that of the visit's trade, and never fills a week above where the week it leaves was, so the peak never rises; at most 30 moves, each visit once. Squared loads were chosen over "lower the peak only" because they also spread the tight weeks and the trades. **Limits** of each move: the ordinary visit move (BR-P3), plus the season, the blocked weeks and **the release horizon**: a visit moved into it would get its work order at the next timeline load, which accepting a proposal must not do as a side effect, and which would make Undo impossible (BR-P4). **Accepting** reuses `PUT /api/plan-occurrences/:id` per move (checked and logged as usual) rather than a batch endpoint: a refused move leaves the others done, reported in the message; the moves done form one Undo step. The client recomputes the figures of the moves ticked (`previewMoves`, same rules as the server's). **Seed**: the busy weeks of the demo plans move from 3, 16, 29, 42 to 5, 18, 31, 44 weeks after the seeding date, so the over-capacity week lies just beyond the release horizon and the assistant can lower it (with the old offsets, its visits had work orders at once and nothing could move them). Also fixed with this phase: when the planner refuses an Undo or Redo, its message now stays on screen (drawing the planner again used to empty it). |
