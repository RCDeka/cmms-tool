# Decisions

This file records the answers to the open questions of the product brief (`docs/SPEC_MVP_GMAO.md`, section "Ce qu'il reste à préciser") and every place where the implementation docs deviate from or complete the brief. When a decision changes, update it here in the same commit.

## Reference hierarchy

1. `docs/SPEC_MVP_GMAO.md`: original product brief (French). Source of truth for **intent and scope**.
2. `docs/data-model.md`, `docs/api-design.md`, `docs/architecture.md`, `docs/ui-guidelines.md`: refined implementation contract. Source of truth for **how**. Where they differ from the brief, the difference is listed below.
3. `docs/roadmap-mvp.md`: order of work and acceptance criteria.

## Answers to the brief's open questions

| # | Question | Decision | Rationale |
|---|---|---|---|
| Q1 | Backend: Flask or Express? | **Node.js 24 LTS + Express 5** | Same language as the frontend; `better-sqlite3` is fast, synchronous and simple. |
| Q2 | Authentication: home-made token or JWT library? | **JWT via `jsonwebtoken`**, passwords hashed with **argon2** | Standard, audited libraries; no home-made crypto. |
| Q3 | Design system | **Neutral, accessible design tokens** (CSS custom properties) defined in `docs/ui-guidelines.md`; system font stack | Brand colors can be swapped later by editing tokens only. |
| Q4 | Main entity of the MVP | **Both** équipements and bons de travaux; équipements are built first | The dashboard and the BT fiche need both; équipements give the earliest demo. |
| Q5 | Mock data | **Entirely fictional**, generated by a deterministic seed script | No real bank data in a prototype. |
| Q6 | Application name | Working title **"Mini-GMAO"**, defined in one place (`APP_NAME` in the frontend config) | Easy to rename when the final name is chosen. |
| Q7 | Concurrent users | Target **up to ~50 concurrent users**; SQLite in WAL mode with `busy_timeout` | Ample for an internal MVP; one writer at a time is fine at this scale. |

## Deviations and additions to the brief

| ID | Topic | Decision |
|---|---|---|
| D1 | Passwords | `users.password_hash` added (the brief's table has no password column). |
| D2 | Versioning on équipements | `version`, `conflit` and `updated_by` added to `equipements` (the brief's `PUT /api/equipements/:id` requires a version, but the table lacked it). `updated_by` also added to `bons_travaux`. |
| D3 | Conflict storage | New table `conflits` stores the rejected client version and a snapshot of the server version. The entity row keeps the server version. |
| D4 | Record frozen during a conflict | While a record has an open conflict, every `PUT` on it is rejected with `409` (`locked: true`) until a supervisor resolves it. Guarantees at most one open conflict per record. |
| D5 | People references on BT | `technicien_assigne` and `superviseur` become foreign keys `technicien_assigne_id` and `superviseur_id` → `users.id` (needed for "Mes interventions du jour" and permissions). The API also returns display names. `equipements.technicien_responsable` stays free text. |
| D6 | Integrity | `UNIQUE` on `equipements.code` and `bons_travaux.numero`; `CHECK` constraints on every enumerated column. |
| D7 | Fiche loading | List endpoints return **complete records**, so the client stores each row as a fiche directly. This replaces the brief's one request per row in `prefetchFiches` (50 requests per page). `GET /:id` is used only on a cache miss or for revalidation. |
| D8 | Extra endpoints | `GET /api/health`, `GET /api/auth/me`, `GET /api/users`, `GET /api/referentiels`, `GET /api/conflits`, `GET /api/conflits/:id`, `GET /api/dashboard`. The brief needs them implicitly (supervisor console, dashboard tiles, dropdowns). |
| D9 | Offline reload | A small **service worker** caches the app shell (HTML, CSS, JS, vendor libraries), so the app also opens offline after a full page reload. API data is cached in IndexedDB only, never by the service worker. |
| D10 | Extra IndexedDB stores | `drafts` (standard-mode autosaves) and `sync_queue` (pending writes) added to the brief's five stores. Fiches are evicted together with their pages, except fiches that have a draft or a queued write. |
| D11 | Offline saves | The offline write queue applies to **both** save modes (the non-functional requirements say edits made offline are synced later). The modes differ only in what triggers a save. |
| D12 | HTML injection | The brief's `renderFiche` sample injects raw values into `innerHTML`. Every value must be escaped or set through `textContent`. |
| D13 | Dates | Datetimes are ISO 8601 UTC strings set by the application; dates are `YYYY-MM-DD`. "Today" and "this month" are computed in `APP_TIMEZONE` (default `Europe/Paris`). |
| D14 | BT workflow | The brief defines statuses but no rules. Allowed transitions and required fields are defined in `docs/data-model.md` (BR-B4 to BR-B7). |
| D15 | Create / delete | The brief defines no `POST` or `DELETE`. Creating and deleting records is **out of the MVP**, and it is the first backlog item. |
| D16 | Language | Domain vocabulary from the brief is kept in French (table, column and JSON field names, enum values, UI labels, URLs). Code identifiers, comments, docs and commits are in English. |
| D17 | Third-party libraries | `idb` and `Chart.js` are vendored into `frontend/assets/vendor/` (no CDN, works offline). No bundler and no build step. |
| D18 | Entity naming map | The brief mixes `eq` / `equipements` / `/equipements` and `bt` / `bons_travaux` / `/bons-travaux`. One entity config object maps store prefix ↔ API path ↔ UI path (see `docs/architecture.md`). |
| D19 | Runtime | Node.js 24 LTS (the brief doesn't specify a version). |
| D20 | Deployment | No Docker. Local development with npm, where Express also serves the frontend. Production: systemd service + Nginx reverse proxy + Let's Encrypt on the VPS. |
| D21 | Power-user mode | Determined by `users.power_user`; the seed sets it to `TRUE` for supervisors and admins and `FALSE` for operators. |
| D22 | Logout | Logout deletes the token and clears IndexedDB. If the sync queue is not empty, the user must confirm first. |
| D23 | Permissions | The brief defines roles but no permissions. The permission matrix is in `docs/api-design.md`. |
